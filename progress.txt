- **Issue**: `TopTaskID` column is used as dimension level key AND in DAX arithmetic expressions

- **Status**: Documented as future work, out of scope for bug-fix PRD

### PFM_from_Daniel_bim.json - TODO stub type conflicts
- **Issue**: Boolean-returning functions (HASONEVALUE, etc.) use `1` as TODO stub for numeric compatibility
- **Problem**: Same stub used in BOTH numeric (`2088 * [HasOneCurrency]`) AND boolean (`[HasOneCurrency] AND [Other]`) contexts
- **Error**: "Function AndOperator requires arguments of type BooleanType$, AttributeValue(...) has type IntType"
- **Root cause**: MDX is type-strict. `1` is IntType, `TRUE` is BooleanType. Can't satisfy both contexts.
- **Required work**: Fundamental type-system handling
  - Option 1: Detect usage context and generate appropriate stub type
  - Option 2: Use `(1 = 1)` which is boolean TRUE but may not work in all arithmetic
  - Option 3: Require users to manually fix TODO stubs (current approach)
- **Status**: Documented as future work, out of scope for bug-fix PRD

## Completed Fixes

(Summary of converter bugs fixed this session)

### Fix 1: BLANK() nested in expressions → NULL
- **File**: `dax-converter.ts`
- **Issue**: When BLANK() appeared inside a larger expression (e.g., `[X]<>BLANK()`), it wasn't being converted to NULL
- **Cause**: FunctionToken.toMdx() didn't have special handling for BLANK - it passed through as `BLANK()`
- **Fix**: Added case for "blank" in FunctionToken.toMdx() switch statement to return "NULL"

### Fix 2: DAX & (string concat) → MDX +
- **File**: `dax-converter.ts`
- **Issue**: DAX uses `&` for string concatenation, MDX uses `+`
- **Error**: "Comma expected but Amp found"
- **Fix**: Added case for "&" in OperatorToken.toMdx() switch statement to return " + "

### Fix 3: Single-quoted column names in DAX brackets
- **File**: `dax-converter.ts`
- **Issue**: DAX allows `['ColumnName']` with single quotes inside brackets
- **Error**: Generated MDX like `[Measures].['TopTaskID']` which is invalid
- **Fix**: Strip single quotes in `parseColumnReference()` when column name is wrapped in quotes

### Fix 4: Perspective searching wrong dimension for attributes
- **File**: `converter-utils.ts`, `perspective-converter.ts`
- **Issue**: `findAttrUse()` searched ALL dimensions, so if `ProjectID` existed as secondary_attribute in dimension_RevBillReceipt, it was used instead of the level_attribute in dimension_Projects
- **Error**: "references secondary attribute that does not exist in dimension"
- **Fix**: Added `dimensionName` parameter to `findAttrUse()` to search only within the correct dimension

### Fix 5: Unquoted table names with spaces in DAX
- **File**: `dax-converter.ts`
- **Issue**: `SUM(Business Plans and Adjustments[Net Income])` was parsed as separate identifiers
- **Error**: Generated `Sum(Business, Plans, and, [Measures].[Net Income])` which is invalid
- **Fix**: Added `mergeUnquotedTableNames()` post-processing to merge consecutive IdentifierTokens before TableColumnReference

### Fix 6: Boolean TODO stubs causing type errors
- **File**: `tools.ts`, `conversion-pipeline.ts`
- **Issue**: HASONEVALUE and similar boolean functions used `FALSE` as TODO stub, causing type errors when used in arithmetic
- **Error**: "Function DividedBy requires arguments of type NumericType, has type BooleanType"
- **Fix**: Changed boolean function fallback to `1` instead of `FALSE` (TRUE=1 in DAX numeric context)

### Fix 7: Encoded metric unique_names not resolving in calculation expressions
- **File**: `measure-converter.ts`, `bim-to-sml-converter.ts`
- **Issue**: Column names with special characters (e.g., `GR Value w/o BOM`) get encoded unique_names (e.g., `GR Value w_o BOM`), but calculation expressions still referenced the original name
- **Error**: "Calculated metric expression contains a non-existing metric: GR Value w/o BOM"
- **Cause**: Base metrics are created AFTER DAX calculations are converted, so lookup fails during conversion; second pass resolution didn't handle filename-encoded names
- **Fix**: Enhanced `resolveUnresolvedReferences()` to also resolve metric name mismatches caused by filename encoding, and added a second call after `measuresFromColumns()` creates base metrics

### Fix 8: ROUNDUP/ROUNDDOWN producing invalid MDX
- **File**: `function-mappings.json`
- **Issue**: DAX `ROUNDUP()` and `ROUNDDOWN()` functions were passed through directly to MDX, but MDX doesn't have these functions
- **Error**: "end of input expected" (MDX parser couldn't parse ROUNDUP)
- **Fix**: Added ROUNDUP and ROUNDDOWN to unconvertible list so they produce TODO stubs instead of invalid MDX

## Completed Fixes (continued)

### Fix 9: COUNTROWS on unused tables producing invalid MDX
- **File**: `measure-converter.ts`
- **Issue**: When COUNTROWS references an unused table, `createAndAddCountRowsMeasure()` returns empty string but caller still created calculation
- **Error**: "Error getting physical type of flat attribute [DocRowCount]: Flat attribute `` not found"
- **Fix**: Added check `if (!referencedMetric)` to skip calculation creation and log warning

### Fix 10: Self-referential cycle in calculated measures
- **Files**: `measure-converter.ts`, `dax-converter.ts`
- **Issue**: When a calculated metric's label matches a base metric's unique_name, `resolveUnresolvedReferences()` would incorrectly remap valid base metric references to the calc's unique_name
- **Error**: "Cycle calculated measure reference detected. Reference path: Post-Close Actual Hours_Current->Post-Close Actual Hours_Current"
- **Root cause**:
  1. Base metric `Post-Close Actual Hours` created for column on `Actuals After LCM` table
  2. Calc metric with label `Post-Close Actual Hours` and unique_name `Post-Close Actual Hours_Current` created for measure on `Current` table
  3. `resolveUnresolvedReferences()` built a `nameToUniqueName` map that didn't prevent calc labels from overwriting base metric unique_names
  4. Expression `[Measures].[Post-Close Actual Hours]` (correct reference to base metric) was remapped to `[Measures].[Post-Close Actual Hours_Current]` (self-reference)
- **Fix**:
  1. Build a `validUniqueNames` set of all metric unique_names (base + calc)
  2. Skip adding calc label→unique_name mapping if label is already a valid unique_name
  3. In second pass, skip remapping if referenced name is already a valid unique_name
  4. Skip calc entries in metricLookup searches (key starts with 'calc')

- US-001: Detect no-relationships scenario
