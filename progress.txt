# Progress Log

## Learnings (from previous sessions)

- EDATE DAX function was not in unconvertible list, causing invalid MDX to be generated
- AtScale MDX does not have an EDATE equivalent for measure expressions
- DAX uses "N/A" strings as null indicators; MDX uses NULL - need to transform comparisons
- AtScale MDX is stricter than standard MDX - test deployments early
- DAX filter context modifications (ALL, column filters) don't translate to MDX
- Type consistency is critical - MDX IIF requires same type in both branches
- Fallback to TODO stub is safer than producing invalid MDX
- DAX BLANK() in nested expressions needs toMdx() handling → NULL
- DAX & operator for string concat → MDX + operator
- BIM measures with sourceColumn but no DAX expression need to be created as base metrics when referenced
- NOW() and TODAY() in DAX often used with date arithmetic - no MDX equivalent, must produce TODO stub
- BIM source files can have bugs (references to non-existent columns/measures) - converter should detect and produce TODO stubs
- Time intelligence conversions (SAMEPERIODLASTYEAR, etc.) depend on dimensions existing - must validate before generating MDX
- resolveDimensionHierarchy() should return undefined when table doesn't exist to trigger TODO fallback

## Iteration 4 - US-003: Fix special character parsing errors in MDX expressions
- **Problem**: Multiple BIM files failed deployment with parsing errors like "Comma expected but OpenParen found"
- **Root causes**:
  1. FIND function passed through literally (no MDX equivalent)
  2. ISBLANK not being converted to ISEMPTY when nested in compound expressions
  3. DAX table literals `{...}` passed through literally (no MDX equivalent in measures)
  4. SAMEPERIODLASTYEAR generating tuple with arithmetic expressions (invalid MDX)
- **Fixes**:
  1. Added FIND, SEARCH, CONTAINSSTRING, SUBSTITUTE, REPLACE, REPT, PATH* to unconvertible list
  2. Added ISBLANK → ISEMPTY to direct_mappings (handles nested ISBLANK in IF conditions)
  3. Made BraceToken.toMdx() throw error to trigger TODO fallback
  4. Added check in SAMEPERIODLASTYEAR template to fail when measure is not a simple reference
- **Files changed**:
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/function-mappings.json` - Added unconvertible functions, ISBLANK mapping
  - `src/commands/bim-to-sml/bim-converter/dax-converter.ts` - BraceToken throws for TODO fallback
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/sameperiodlastyear-template.ts` - Check for simple measure ref
- **Learnings for future iterations**:
  - DAX string functions (FIND, SEARCH, etc.) have no MDX equivalent for measure expressions
  - Direct function mappings handle nested cases better than templates (for simple 1:1 mappings)
  - DAX table literals are not valid in MDX measure expressions
  - MDX tuple syntax `(set, measure)` requires both parts to be members, not expressions
- **Verified**:
  - Dealer_Performance_Dashboard_bim.json deploys successfully
  - Global_Report_-_Assembly_KPIs_bim.json deploys successfully
  - HDNA_Magellan_Report_bim.json deploys successfully
  - Most_Loved_bim.json deploys successfully
  - npm run test-custom-calcs passes (54% conversion rate maintained)

## Iteration 5 - US-004: Fix data type mismatches in function arguments
- **Problem**: Time intelligence functions (TOTALYTD, SAMEPERIODLASTYEAR, etc.) generated invalid MDX when dimension hierarchy lacks required time levels
- **Root cause**: `resolveTimeLevelByUnit()` returned fallback string like "Year" when no matching level exists, causing MDX to reference non-existent hierarchy levels
- **Fixes**:
  1. Changed `resolveTimeLevelByUnit()` to return `undefined` instead of fallback when time level doesn't exist
  2. Updated SAMEPERIODLASTYEAR, PREVIOUSMONTH, PARALLELPERIOD templates to fail conversion when required time level is missing
  3. Updated TOTALYTD template to validate Year level exists before generating YTD() MDX
  4. Updated TOTALMTD template to validate Month level exists before generating MTD() MDX
  5. Updated TOTALQTD template to validate Quarter level exists before generating QTD() MDX
- **Files changed**:
  - `src/commands/bim-to-sml/bim-converter/converter-utils.ts` - resolveTimeLevelByUnit returns undefined
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/sameperiodlastyear-template.ts` - year level validation
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/previousmonth-template.ts` - month level validation
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/parallelperiod-template.ts` - time level validation
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/totalytd-template.ts` - year level validation
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/totalmtd-template.ts` - month level validation
  - `src/commands/bim-to-sml/bim-converter/conversion-templates/templates/totalqtd-template.ts` - quarter level validation
- **Learnings for future iterations**:
  - Time intelligence MDX functions (YTD, MTD, QTD, ParallelPeriod) require specific hierarchy levels to exist
  - Flat date dimensions with only a Day level don't support YTD/MTD/QTD patterns
  - "Fail fast" by returning undefined from utility functions instead of fallback values
  - Time level validation should happen before generating MDX, not during deployment
