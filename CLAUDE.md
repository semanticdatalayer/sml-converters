## Project Overview

**sml-converters** is a CLI tool for converting between semantic modeling formats and the Semantic Modeling Language (SML). It bridges various business intelligence and data warehouse modeling tools. Details for each of the conversions, if any, are provided in their respective src/commands/\* folders

**Supported conversions:**

- DBT → SML
- Power BI Model (BIM) → SML
- SML → Snowflake Cortex Analyst YAML
- Upload Cortex YAML to Snowflake

## Architecture Patterns

### Converter Pipeline Pattern

Every converter follows a consistent 3-stage pipeline:

1. **Parse** → Read and validate source format
2. **Convert** → Transform to target format using converters
3. **Persist** → Write output files

### Core Design Patterns

**SmlConvertResultBuilder** (Builder Pattern)

- Central accumulator for all SML objects during conversion
- Located: `src/shared/sml-convert-result.ts`
- Validates `unique_name` uniqueness across ALL SML objects (critical!)
- Prevents duplicate object registration
- Usage: Add objects via `.add<ObjectType>()` methods

**Converter Architecture** (Strategy Pattern)

- Each format has dedicated converter modules with specialized converters
- DBT: `DbtConverter` + `DbtParser` + `DbtCalculations` + `DbtTools`
- BIM: `TableConverter`, `DimensionConverter`, `MeasureConverter`, `RelationshipConverter`, `DatasetConverter`, `PerspectiveConverter`
- Cortex: `CortexConverter` + `SnowConverter`

**Guard Pattern**

- Location: `src/shared/guard.ts`
- Provides validation and error handling throughout the codebase
- Methods: `should()`, `exists()`, `notEmpty()`, `ensure()`, `ensureType()`
- Always use Guard for precondition validation

### Component Separation

```
Commands (src/commands/*-command.ts)
    ↓ orchestrates
Parsers (*-parser.ts)
    ↓ validates and parses input
Converters (*-converter.ts)
    ↓ transforms to target format
    ↓ uses SmlConvertResultBuilder
Writers (SmlResultWriter)
    ↓ persists to disk
```

## Key Architectural Details

### SML Unique Names

**Critical Convention:** All SML objects must have globally unique `unique_name` values.

Format: `<type>.<friendly_name>` (e.g., `model.sales_model`, `dim.customer`)

- Generated by: `makeUniqueName()` utility
- Validated by: `SmlConvertResultBuilder`
- Auto-suffixing for duplicates: `SmlUniqueNameGenerator` adds "(1)", "(2)", etc.

### Logger Pattern

Every component receives a `Logger` instance:

- Created via: `CommandLogger.for(command)`
- Levels: error, warn, info, http, verbose, debug, silly
- Colors: red (errors), yellow (warnings)

### File Organization

Output structure created by `SmlResultWriter`:

```
<output>/
├── catalog.yml (root catalog file)
├── models/
├── dimensions/
├── datasets/
├── metrics/
├── calculations/
├── connections/
└── security/
```

File names are encoded to handle invalid characters (see `encodeFileName()` in `src/shared/file-system-util.ts`).

### Data Warehouse Types

Enum: `DWType` in `src/shared/dw-types.ts`

- Supported: BigQuery, Snowflake, Postgresql, DataBricks, Iris
- Affects identifier casing (upper/lower) in conversion logic

### How Queries Work in AtScale

AtScale exposes an SML semantic layer as a single logical (virtual) table.
Each column in this virtual table represents a semantic object, including:
• Metrics and metric calculations
• Level attributes and secondary attributes
• Dimension metrics
• Level aliases

#### Inbound Queries

BI tools and agents issue inbound queries against this virtual table:
• Most tools generate simple SQL that references semantic columns by name (not physical tables).
• Excel and some OLAP tools generate MDX, which references the same semantic objects via cubes, dimensions, levels, and measures.

Inbound queries never reference physical schemas, tables, or columns.

#### Translation

AtScale parses the inbound query (SQL or MDX) and: 1. Resolves each referenced semantic column to its underlying SML definition. 2. Determines the required joins, aggregations, filters, and calculations. 3. Generates one or more outbound SQL queries.

#### Outbound Queries

Outbound queries are database-specific SQL executed directly against the underlying platform (Snowflake, BigQuery, Postgres, etc.) and reference:
• Physical tables and columns
• Engine-appropriate SQL syntax
• Optimized join and aggregation strategies

#### Key Principle

Inbound queries operate purely on semantic objects defined in SML and must never reference physical tables or columns. Outbound queries operate purely on physical data. SQL and MDX inbound queries follow the same semantic resolution pipeline—the only difference is the front-end query language.

## Important Utilities

**SmlConverterQuery** (`src/shared/sml-converter-query.ts`)

- Query interface for finding existing SML objects by unique_name or other properties
- Use when you need to reference previously converted objects

**file-system-util** (`src/shared/file-system-util.ts`)

- `parseInput()`: Validates source/output paths
- `cleanUpOutputFolder()`: Handles `--clean` flag (preserves `.git`)
- `encodeFileName()`: Replaces invalid filename characters

**yaml-parser** (`src/shared/yaml-parser.ts`)

- Wraps `js-yaml` for consistent YAML parsing

**composite-model-util** (`src/shared/composite-model-util.ts`)

- Handles SML CompositeModel conversion (combines multiple models)
